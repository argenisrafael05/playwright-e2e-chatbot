# Technical decisions

The main decisions behind these tests, why they were made and what else was considered.

| Decision                                                       | Why                                                                                                                       | How it's handled                                                                                                                                                                                           | Also considered                                                                                                                                                             | Trade-off                                                                                                            |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Test a real third-party bot, the ChatBot.com sample chat       | A real bot is unpredictable, and that's the real challenge. The same "Hola" has already gotten three different greetings  | The reply is checked by intent, not by exact text. The bot has its own page object and pipeline job, and the tests never pick an option that sends the chat to a person                                    | Building a small bot for the tests. It would always answer the same, so there'd be nothing real to test                                                                     | If the site changes or goes away, the bot gets replaced                                                              |
| The reply is the first message after "Hola", checked by intent | The chat greets on its own, and the welcome is a greeting too. Taking the first message would pass without sending "Hola" | The visitor's message is found by its text and the next one is the reply. It passes if it has a greeting from a list. The 15-second wait is on the text, because the bot shows an empty "typing" row first | Counting messages, which breaks when the bot removes its menu. The author's CSS classes, which are generated                                                                | A new greeting fails the test until it's added to the list                                                           |
| Page objects with fixtures, and the assertions in the tests    | Several tests share the same pages, and each test should show what it checks                                              | Page objects have read-only locators and actions. Fixtures hand them to the tests, and the tests check with assertions that wait on their own                                                              | Assertion methods inside the page objects, which hide what each test checks                                                                                                 | One more layer, in exchange for tests that read like the behavior they check                                         |
| Locators the way a user sees them                              | They read like the page and survive layout changes                                                                        | Role and name first, then label, placeholder and text. CSS only where the demo gives nothing better, with a comment saying why                                                                             | CSS or XPath by page structure, quick to write and quick to break. Test ids, which can't be added to a system that isn't ours                                               | A few CSS locators remain: the chat frame by its id, the forms, fields with unlinked labels and the attachment icons |
| Fresh data on every run, and only our own data gets cleaned up | The OrangeHRM demo is public. Other people change its data and settings, and it resets                                    | Unique data per run. The attachments test only touches rows with its own comment and deletes them, even if it fails halfway. Dates follow the format the field shows as its hint                           | Fixed data, which collides with other runs. A fixed date format, which fails as soon as someone changes the setting                                                         | The personal details stay changed, since a shared demo that resets has no original to restore                        |
| One login for the web tests                                    | Almost every web test needs a logged-in user, and the demo is slow                                                        | A setup project logs in once and saves the session. Login and logout start without it, so a logout never touches it                                                                                        | Logging in inside every test, slower and more load on the demo                                                                                                              | Sessions expire, so the tests that save data check it first and fail with a clear message                            |
| Flaky tests and outages stay visible                           | Both sites are public demos. Some days they're slow, some days they just don't answer                                     | One retry in CI, none locally. A test that only passes on the retry shows up as flaky. Each failure gets a verdict: our bug, or a site that didn't answer                                                  | More retries or bigger timeouts, which make the runs greener and the report less honest                                                                                     | A green run can still carry a flaky test, and someone has to look at it                                              |
| One pipeline, one report                                       | The tests should run on every change, and a failure should say which part broke                                           | GitHub Actions on every push to `main` and by hand. Formatting, types and linting first, then both suites in parallel. One merged report, even if a part failed, published on GitHub Pages                 | Jenkins, which needs its own server. A daily run, which would hit the third-party sites for nothing. A smoke job first, which would stop the web tests when the bot is down | If the demo is down, the login fails and the web tests don't start                                                   |
